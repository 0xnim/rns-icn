rns-icn: what changed and what it measured

ICN (content fetched by name, cached at a hub) compared with fetching a NomadNet-style page from its origin, over Reticulum links limited to 1,200 bit/s. Measured 2026-11-16 with bench/run.py; single runs, one to three readers per method.

1. The network, and where ICN nodes go

An example mesh: two villages and a lone reader, all reaching a remote publisher over slow radio links. Pick a situation to see which links carry the item. Only three kinds of node run ICN; relays and page browsers need nothing new.

The hop counts in this section are counted from the drawing to show the pattern. The measured numbers start in section 3 and come from a three-node version of this mesh: one reader, one hub, one origin.

2. What changed in the code

About 540 lines changed in 15 existing files, plus new modules, tests and the benchmark. Blue is new behaviour; orange is a fix for a bug that was already there.

3. Carrying a fetch: before and after

Every packet on the reader's link for one 200-byte item, from link setup to the answer. The packet trace showed the extra cost was acknowledgements and a handshake, so reader fetches now use Reticulum's request/response, as NomadNet does.

reader to hub hub to reader

Sizes are measured, including link framing. What each packet is was inferred from its size and position, not decoded. Both cases also spend about 420 bytes before this on interface setup, a path request and the hub's announce.

4. Results: slow backhaul, fast reader link

The case a caching hub is for: readers on the hub's Wi-Fi, the origin behind a 1,200 bit/s link. Grey is the existing page fetch; blue is ICN in three states of the hub's cache.

The 2 KB cold ICN fetch used 4,988 backhaul bytes, about twice the item: something was retransmitted. Earlier clean runs of the same fetch used 2,612 to 2,804.

5. Results: both links at 1,200 bit/s

With the reader's link slow too, the cache saves the backhaul leg but the reader still waits for its own link. This is also where the remaining failure showed up.

6. The bug behind the early failures

The link pool closed any link nobody had asked it for in 120 seconds, whether or not it was in use. A hub asks for its upstream link once and then keeps using it, so the link was cut mid-transfer and the hub's route to the origin went with it.

7. What is still open

A cold fetch of a 2 KB item over slow links is not reliable yet: it timed out once with both links slow, after about three times the item's size had crossed the backhaul. The likely cause is large messages being resent because Reticulum's timers do not know the link is slow, possibly made worse by the benchmark relay offering an 8 KB packet size. That is not confirmed.
